# Portuguese plugin preference migration

Migration in the current [PR 31574](https://github.com/stablyai/orca/pull/31574), alongside the built-in Portuguese support in commit `9050297eefa`. Change an existing exact `plugin:stablyai.orca-portuguese/pt-BR` preference to built-in `pt` once per local profile or browser settings store. Keep the plugin available for deliberate later selection.

## Evidence and decision

- `9050297eefa` adds `pt` to the language type, supported locales, picker, and both lazy catalog loaders; it changes no migration or plugin files. The built-in catalog comes from the community contribution [PR 26656](https://github.com/stablyai/orca/pull/26656), not from the official plugin's source. Marketplace ownership is not catalog provenance. Retain this community credit in the current PR description.
- [`normalizeUiLanguage`](../../src/shared/ui-language.ts) preserves syntactically valid plugin IDs; the same function handles persisted loads **and live updates**. [`resolveUiLocale`](../../src/shared/ui-locale.ts) also preserves them. Neither currently treats this plugin as an alias for `pt`.
- Desktop load splits dirty marking in [`prepare-loaded-profile-settings.ts`](../../src/main/persistence/loading-store/prepare-loaded-profile-settings.ts) from settings assembly in [`normalize-loaded-global-settings.ts`](../../src/main/persistence/loading-store/normalize-loaded-global-settings.ts). Browser [`getStoredSettings`](../../src/renderer/src/web/preload-api/web-preferences-store.ts) normalizes and conditionally rewrites `orca.web.settings.v1` in localStorage.
- Before a normal profile load, the [offline hook toggle](../../src/main/persistence/profile-state/profile-state-offline-settings.ts) can merge defaults into stored settings and persist them. Inactive project transfer also merges settings defaults in [`normalizeProfileProjectState`](../../src/main/orca-profiles/profile-project-state-file.ts); [`prepareProfileProjectDomainChanges`](../../src/main/orca-profiles/profile-project-domain-changes.ts) compares every domain, including settings, for persistence. A new `true` default would let either path stamp an existing plugin preference without converting it, causing the eventual load helper to skip conversion.
- The [`language pack registry`](../../src/main/plugins/plugin-language-pack-registry.ts) identifies packs by plugin key and declared locale. Its [base registry](../../src/main/plugins/plugin-artifact-pack-registry.ts) requires approval and verified content. [Renderer](../../src/renderer/src/i18n/I18nProvider.tsx) and [main](../../src/main/i18n/main-i18n.ts) fall back to English for an unavailable selected pack; installation alone does not guarantee a registered pack.

A flag is unnecessary if we leave selection manual: PR 31574 already lets users choose built-in Portuguese. It becomes necessary for **automatic conversion plus later plugin reselection**. An unguarded load rewrite produces `old plugin → pt → user selects plugin → restart → pt`; changing the common normalizer rejects the user's selection immediately. Idempotence on `pt` does not solve that distinction. No existing language migration receipt covers it; the persisted-state `SCHEMA_VERSION` is still `1`, not a per-preference rollout history.

Use one optional boolean, `GlobalSettings.uiLanguagePortugueseMigrationApplied`, and one pure load-only helper in `src/shared/portuguese-ui-language-migration.ts`. This follows the existing [cursor default](../../src/shared/terminal-cursor-style-settings.ts) and [branch rename](../../src/shared/auto-rename-branch-from-work-settings.ts) migrations without introducing a version registry, startup service, or plugin lifecycle hook. “Applied” means the store has been considered, even when its language was unchanged.

## Rules

The helper accepts partial stored settings, uses the **raw, exact, case-sensitive** language value for matching, and returns the language/marker pair:

| Stored marker                  | Stored language                          | Result                               |
| ------------------------------ | ---------------------------------------- | ------------------------------------ |
| Anything except boolean `true` | `plugin:stablyai.orca-portuguese/pt-BR`  | `pt`, `true`                         |
| Anything except boolean `true` | Any other value                          | `normalizeUiLanguage(value)`, `true` |
| Boolean `true`                 | Any value, including the exact plugin ID | `normalizeUiLanguage(value)`, `true` |

- Preserve `system`, other built-ins, other publishers, other Portuguese packs, and spelling/case variants accepted by the existing normalizer. Do not use prefix, locale-family, or plugin display-name matching.
- Stamp **all** existing stores on their first normal desktop/browser settings load, not just matching stores. Otherwise a currently English profile could choose the plugin later and be migrated on its next load. New defaults carry `true` so fresh profiles never enter the legacy cohort. An unrelated write before that first load must preserve the raw marker instead of inheriting the new default.
- Keep `UiLanguage`, `normalizeUiLanguage`, and locale resolution semantics unchanged. An explicit later plugin selection must survive saving, reloading, profile switching, and plugin refresh.
- Do not uninstall, disable, revoke consent, delete plugin data, change installation provenance, or require a plugin-service/network lookup. Missing, disabled, unapproved, or broken plugin installations receive the same preference conversion. Only these two settings fields change as a result of this migration.

## Wiring and persistence

1. **Types/defaults:** add the optional marker beside `uiLanguage` in [`global-settings-types.ts`](../../src/shared/global-settings-types.ts); seed `true` beside the existing `system` default in [`default-global-settings.ts`](../../src/shared/default-global-settings.ts). Do not change the default language.
2. **Desktop load:** compute the pair from `parsed.settings` in `prepareLoadedProfileSettings`, before defaults can hide an absent marker. Return it in `PreparedLoadedProfileSettings`; call `markNeedsSave()` whenever either stored field differs. Spread that pair in `normalizeLoadedGlobalSettings` instead of separately normalizing `uiLanguage`.
3. **Existing-store hydration:** in the two settings merges below, make a local copy of settings defaults with only `uiLanguagePortugueseMigrationApplied` omitted, then spread the raw stored settings over it. Preserve the raw marker's value or absence: an absent key stays absent in the serialized settings, `false` and malformed values remain unchanged, and a stored `true` survives. Missing or non-object settings in an existing store must not acquire a receipt either. Keep the stored language unchanged and do not call the migration helper here.

   - In [`updateAgentHookSettingsInProfileState`](../../src/main/persistence/profile-state/profile-state-offline-settings.ts), apply this to the defaults merged with the raw `persistedSettings` row before the hook toggle writes it. This also covers legacy JSON adopted by `updateAgentHookSettingsFromProfileState` before that write.
   - In [`normalizeProfileProjectState`](../../src/main/orca-profiles/profile-project-state-file.ts), use the marker-omitting defaults for both the `parsed.settings` merge and its missing/non-object fallback. The resulting transfer state can pass through the existing all-domain comparison and write without manufacturing a receipt for either inactive participant.

   Derive these copies without mutating the shared defaults. Keep fresh defaults stamped, including the offline no-storage initializer and transfer reader's separate `parseProfileState(undefined)` branch. Missing settings in a persisted root do not prove a store is new. These two local omissions are the entire pre-load fix; transfer domain selection, revision checks, secret handling, and storage adoption stay unchanged.

4. **Desktop durability:** use the existing [`loaded-state-parsing.ts`](../../src/main/persistence/loading-store/loaded-state-parsing.ts) → `loadNeedsSave` → [`Store`](../../src/main/persistence/loading-store/store.ts) scheduled save. The existing [settings serializer](../../src/main/persistence/loading-store/state-serialization-secret-handling.ts) writes the pair together through the profile's SQLite authority. No direct JSON file writes or new persistence layer. Frozen imports normalize in memory without modifying their source; the destination persists the normalized state. Inactive profiles migrate on their normal settings load, without an eager profile scan or conversion during project transfer.
5. **Browser load:** spread the same helper's result into `migratedStored`; retain the language comparison and add an explicit marker comparison to the existing rewrite predicate. Preserve the raw valid-object guard and non-destructive handling of invalid JSON, arrays, primitives, and absent storage. Empty stores receive the stamped defaults in memory; the next ordinary settings write persists them. Do not rely on the current `terminalCustomThemes` reference comparison, which incidentally causes extra writes on reads.
6. **Explicit writes stay unchanged:** desktop [`settings-update.ts`](../../src/main/persistence/applying-settings/settings-update.ts) and browser [`mergeSettings`](../../src/renderer/src/web/preload-api/web-preference-normalization.ts) spread the current settings before the update. Ordinary `{ uiLanguage: selectedValue }` updates therefore retain the already-stamped marker. Do not invoke the helper on live updates or add marker branches to either writer. The marker is internal metadata with no supported user control or RPC mutation; manually deleting/resetting it has the same semantics as restoring an unstamped backup. No picker change is needed.

Language and marker remain local to the desktop profile or browser origin. Runtime [`settings.get/update`](../../src/main/runtime/runtime-client-settings-shape.ts) and the strict [`SettingsUpdate` RPC schema](../../src/shared/rpc-contract/client-settings-params.ts) omit language; omit the marker too. Keep browser runtime synchronization's existing allowlist. New clients migrate locally with old servers and vice versa, without a capability or protocol change. Mobile has no `uiLanguage` consumer; this does not add mobile localization. The rule is platform independent and does not depend on whether a workspace is a folder or git worktree.

## Downgrade and plugin availability

Keep the bundled [marketplace entry](../../resources/plugins/launch/orca-marketplace.json), Portuguese plugin, repository/tag, and approved registrations intact. Old clients must still be able to discover/install the plugin; new clients may deliberately select its separate picker entry. Catalog retirement or a marketplace deprecation notice is separate work.

A build containing `pt` but predating this migration can still render the migrated preference. A build **without** built-in `pt` normalizes it to `system`; its supported OS locale determines the resulting language (English for a Portuguese OS locale in the immediate pre-`pt` build), and saving settings can persist that fallback. Keeping the plugin installed does not automatically restore its old selection. Users can select the retained plugin in a compatible older client, then keep that choice on re-upgrade if the marker survives. Nearby builds preserve unknown settings through object spreads, but arbitrary older builds or backups may discard the marker; a restored unstamped snapshot is considered legacy again. Do not promise reversible preference conversion or seamless downgrade.

Independently, builds older than the [SQLite profile release floor](../../src/shared/profile-state-build-compatibility.ts), `1.4.214`, require the existing per-profile state rollback procedure. This preference migration neither changes nor bypasses that storage restriction.

## Verification and boundaries

Implementation tests should exercise production functions and public storage paths:

- Table-test the helper: exact match; boolean `true`; missing/false/malformed marker; system/other built-ins; other plugin IDs, case and locale variants; invalid/missing language; repeated application. Assert ordinary `normalizeUiLanguage` still accepts the exact plugin ID.
- Extend desktop load/settings tests with an otherwise fully migrated profile, removing only this marker. Advance fake save timers and await the actual authority write **without an unconditional flush**, then reopen and check both fields. Also test a nonmatching language receives a durable marker and that a fresh profile can select the plugin without conversion. Follow the existing [isolated dirty-mark test](../../src/main/persistence-clipboard-selection-migration.test.ts) pattern; unrelated migrations must not make a missing dirty mark pass.
- Add focused write-then-load regressions to the existing [offline settings](../../src/main/persistence/profile-state/profile-state-offline-settings.test.ts) and [project domain transfer](../../src/main/orca-profiles/profile-project-domain-transfer.test.ts) suites. Seed the exact plugin preference without a marker, toggle hooks through the JSON/SQLite fixtures or move a project between inactive profiles, and inspect persisted settings before any normal load: the plugin value and marker absence must survive in every written participant. Then perform a normal Store load and scheduled save, reopen, and assert `pt` plus `true`. Repeat with an already-stamped plugin reselection to prove each unrelated write and subsequent load preserve that choice. Focused hydration assertions should also cover raw `false`/malformed markers and missing/non-object settings; fresh defaults and the offline no-storage initializer must still carry `true`. Reuse the existing fixtures and Store harness rather than building a new persistence test framework.
- Extend [`web-preload-api-settings.test.ts`](../../src/renderer/src/web/web-preload-api-settings.test.ts): read `get/getSync`, inspect localStorage, recreate the API, and reselect the exact plugin via `settings.set`. Cover a legacy nonmatching store, a fresh store, malformed raw storage, and preservation of unrelated fields. Assert no language/marker runtime update is sent, including with an older/offline runtime. Do not assert globally write-free reads while the unrelated theme normalization still writes.
- On both paths, verify later explicit plugin selection and unrelated updates survive reload with the marker retained. Check plugin install/data/consent fixtures remain unchanged. Exercise built-in renderer/main lazy loading without a registered plugin, then a registered plugin reselection. A background Electron CDP smoke check should show built-in Portuguese selected after upgrade and the plugin still separately selectable.
- Check an immediate pre-`pt` normalizer maps persisted `pt` to `system`; separately verify an older marker-preserving settings round trip before claiming that downgrade/re-upgrade preserves plugin reselection. Run focused tests with `ORCA_BACKGROUND_LAUNCH=1`, typechecks, and the changed-code quality gate when implementing.

**Prerequisite:** include the built-in type, picker, loaders, and vetted community catalog from `9050297eefa` with this migration in PR 31574. Translation quality/coverage fixes, unavailable-pack fallback improvements, and marketplace messaging remain separate work. A fallback-only root fix can avoid English when a pack is unavailable, but leaves installed approved packs selected and does not migrate the preference; registry suppression would prevent deliberate reselection. Neither substitutes for this scoped migration. No new notice, consent flow, schema-version bump, reverse mapping, generalized migration framework, or additional migration helper for the two hydration merges is required.
